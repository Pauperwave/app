## Method and its limits

The comparison is against `shared/utils/types/database.ts`, which is generated by `pnpm supabase:types` from the live database. That file is authoritative for **tables, columns, nullability, foreign keys, views, functions and enums**.

It does **not** express check constraints, indexes, RLS policies, triggers or defaults-with-expressions. So every claim below about columns and FKs is verified; claims about check constraints and RLS are taken from the backup docs and flagged as *unverified against the live DB*. Confirming those needs a session against the database itself.

## Headline

The backup docs are a **design document, not a description of what was built**. They were clearly written before/while the schema was being created and were not maintained afterwards. Roughly a third of the live schema is undocumented, three documented tables were never built (or were dropped), and one whole subsystem was redesigned into a different shape.

They remain valuable — the naming conventions, the reasoning about cascade rules, and the RLS policy templates are all still relevant — but they cannot be used as a reference for what the database currently is.

The live `organizations` table (`name`, `type`, address fields, contacts) looks like the answer, but nothing in the generated types links `events` to it — worth checking whether the link was ever made.

## 2. `commander_decks` was redesigned, not merely renamed

Documented shape (`2-database.md:801`): `name`, `combo_name` (FK → `mtg_color_combinations.combo_name`), `decks_archetypes_id` (FK → `deck_archetypes.uuid`), plus commander/companion names — and ownership expressed through the `player_decks` join table (many-to-many).

Live shape: `commander_1_name`, `commander_2_name`, `companion_name`, `decklist_url`, `created_at`/`updated_at`, and a direct **`player_uuid` FK → `players.uuid`**.

So: colour-combination and archetype classification were dropped entirely, and the many-to-many collapsed into a one-to-many (a deck belongs to one player). That accounts for all three missing tables at once. Nothing in the docs records this decision or its rationale.

## 5. Findings that bear directly on the Campionato Cittadino (BACKLOG P1)

1. **The premise holds.** Neither the docs nor the live schema contain any cross-tournament championship concept. There is nothing to reuse and nothing to migrate — it is genuinely new.
2. **`ruleset__points` is a weaker reuse candidate than it first appeared.** `2-database.md:993` puts a check constraint on it allowing only `kill, rank_1, rank_2, rank_3, rank_4, brew, play, participation`. The cittadino table needs placements down to *10th and below*, so `rank_5`…`rank_10` have nowhere to go without altering the constraint. Beyond that, the table is scoped per **ruleset**, and rulesets attach to **leagues** (`leagues.ruleset_uuid`) — precisely the axis the user confirmed the cittadino is *not* on. *(Unverified: the generated types don't expose check constraints, so confirm the constraint still exists before treating this as decided.)*
3. **`tournaments.event_uuid` being nullable is good news.** The regulation counts one-off events (draft, sealed) alongside league events; the live schema already permits a tournament that hangs off no event.
4. **Two candidate sources for placement.** `tournament_standings.player_rank` (nullable, one row per player per tournament, unique per registration) is the natural one. `tournament_round_results.position` is per-round and finer-grained. The cittadino needs *final* placement, so `tournament_standings` is the right source — but it is nullable, so nothing guarantees it is populated.
5. **The public-read RLS the cittadino page needs may already be designed.** `3-RLS-policies.md:117` proposes `public_read … USING (true)` on `tournament_standings`, and the same on `tournaments` and `players`. If those were applied, a public standings page needs no new policy. *(Unverified — and note `docs/BACKLOG.md` P1 already records that at least one table got an overly-permissive catch-all policy instead of the designed one, so "documented" ≠ "applied" here.)*

## 6. Documents that are wholly superseded

- **`api.md`** describes `server/api/v1/` with REST verbs across `leagues`, `associates`, `events`, `tournaments`, `rounds`, `pairings`, `positions`, `results`, `scores`, `players`, `rulesets`, `archetypes`. The live `server/api/` has no `v1` prefix and none of that structure: it is `check-associate.post.ts`, four static-data handlers (`leagues.ts`, `members.ts`, `notifications.ts`, `tournaments.ts`), `cardtrader/*`, and the `wanted-cards/*.post.ts` BFF endpoints. The BFF `*.post.ts` convention (ADR-007) replaced this design outright.
- **`4-useful-SQL-queries.md` contains at least one query that cannot run.** Line 44 joins `pauperwave_associates a ON a.id = p.associate_id`; `pauperwave_payments` has no `associate_id` column — it has `associate_uuid`, referencing `associates.uuid`. Separately, the standings query at lines 22-25 joins through `tournament_registrations` to filter by tournament, which is unnecessary now that `tournament_standings.tournament_uuid` exists — the doc's own TODO at `2-database.md:574` asking for that column is stale, since the column is right there in the `CREATE TABLE` below it.
- **`blog.md`** was not assessed against the schema; it is not schema documentation.

## Recommendation

Do not merge these docs into `docs/` as-is, and do not treat them as a source of truth. Two things are worth salvaging, in this order:

1. **Before any cittadino schema work:** verify against the live database the three items flagged *unverified* above — the `ruleset__points` check constraint, whether `public_read` was actually applied to `tournament_standings`/`tournaments`, and whether `assign_role` exists under another name. All three change the shape of the work.
2. **Separately, and not urgently:** the naming conventions (`2-database.md:5-9`), the index guidance (`:11-15`), and the RLS policy templates (`3-RLS-policies.md`) are still good and are not written down anywhere in `app/docs/`. They belong in `docs/architecture/` as a database conventions doc. The per-table `CREATE TABLE` dumps do not — the generated types already serve that purpose and cannot drift.

The full 26-table systematic audit already queued in `docs/TODO.md:9` is the right vehicle for reconciling the rest; this comparison narrows its starting point to the 13 undocumented tables and the drifts in §3.
