- **Drop overly-permissive RLS policy on `pauperwave_associates`.** The policy `"Only auth users can do things"` (`FOR ALL`, role `authenticated`, `USING (true)`, no `WITH CHECK`) grants any logged-in user full SELECT/INSERT/UPDATE/DELETE on every associate row — tax codes, birth dates, home addresses — and overrides the narrower `player_own_associate` and `management_full_access` policies, since Postgres RLS policies are OR'd together. Fix: `DROP POLICY "Only auth users can do things" ON public.pauperwave_associates;` then verify access still works as expected for management and self-service applicant flows.
  - Found: 2026-08-05, via manual RLS policy review.
  - Follow-up: audit other tables (`players`, transactions, tournaments, etc.) for the same catch-all-policy pattern before considering this closed.

- **Build the "Campionato Cittadino" ranking (2026 edition) — cross-tournament standings + public page.** Confirmed by the user 2026-08-09 as an orthogonal axis to leagues, not a league: a tournament can belong to a league *and* count for the cittadino, or count for it with no league at all. Official regulation ("Regolamento Campionato Cittadino '26 di Rovereto by Pauperwave") supplied by the user, summarized below.
  - **Rules, as given:**
    - *Eligibility:* every calendar event from January to December 2026 counts — those inside the pauper / premodern / casual commander leagues **and** one-off events (draft, sealed) — **except finals and side events**. Participation in all events is not required.
    - *Points by final placement:* 1st 25, 2nd 18, 3rd 15, 4th 12, 5th 10, 6th 8, 7th 6, 8th 4, 9th 2, 10th and below 1.
    - *Aggregation:* only each player's **best 11 scores** count toward the final standings — not the sum of all results.
    - *Tie-break:* higher single-event score wins.
    - *Final:* the top 16 play a dedicated "cubo draft" event in January 2027, with booster prizes, for the cup and the title of "campione di città della Quercia anno 2026".
    - *Publication:* standings updated and published **monthly** on the public board.
  - **Why P1 despite not being requested as urgent:** the 2026 edition is already running — it started in January and standings were meant to be published monthly. As of August 2026 that's ~8 months of events whose placements the app has never recorded, so this is a backfill problem as much as a feature. Confirm how many 2026 tournaments already have `tournament_standings` rows before estimating effort; if that table is largely empty, entering historical placements is the bulk of the work and is a prerequisite for any standings page being meaningful.
  - **Schema shape — decided and migrated (2026-08-09).** A year-scoped `cittadino_editions` table (the title is explicitly per-year, and the user described it as "una cosa che dura ad esempio un anno"), plus a nullable `cittadino_edition_uuid` FK on `tournaments`, independent of `league_uuid` and `event_uuid` (confirmed 2026-08-09: a tournament can belong to a league and/or an event and/or count for the cittadino, all independently, or be disconnected from all three) — that FK *is* the per-tournament "valido per il cittadino" switch, and leaving it `NULL` is how finals and side events are excluded. See `supabase/migrations/20260809140000_create_cittadino_editions_and_tournament_fk.sql` — pushed to the remote project and `shared/utils/types/database.ts` regenerated (2026-08-09). `cittadino_editions` has no rows yet (the 2026 edition still needs to be inserted) and nothing writes `tournaments.cittadino_edition_uuid` yet — both are still open, see the "Next step" below. Points come from `tournament_standings.player_rank`, which already exists per player per tournament. Note the aggregation cannot be a plain `SUM`: best-11-of-N needs a windowed query (rank each player's results per edition, sum where `row_number() <= 11`), with the tie-break reading the max single result.
  - **Reuse candidate, largely ruled out (2026-08-09).** `rulesets` + `ruleset__points` (`category` text, `points` int, `ruleset_uuid` FK) looks shaped like a placement→points map, but the audit in `docs/audits/2026-08-09-backup-docs-vs-live-schema.md` found two problems: the documented check constraint only allows `kill, rank_1..rank_4, brew, play, participation`, so `rank_5`…`rank_10` have nowhere to go; and the table is scoped per *ruleset*, while rulesets attach to *leagues* (`leagues.ruleset_uuid`) — the very axis the cittadino is not on. Verify the constraint against the live DB (generated types don't expose check constraints) before closing this off, but plan for a dedicated points table.
  - **Presentation: a players × events matrix, and PDF is the delivery format.** Clarified by the user 2026-08-09: the standings as they exist today are one large crosstab — one row per player, one column per event, the cell holding that event's points — and the artifact that goes on the board is an **exported PDF**, not a page people read on a phone. That rules out the interaction-based answers to the density problem (expandable rows, progressive disclosure): a PDF has no interaction, so every counted and dropped result has to be on the sheet at once. It also makes the "best 11" rule a per-cell visual state (counted vs. dropped) inside the matrix rather than a separate breakdown view.
  - **Public-subdomain consequence — now uncertain, confirm before building.** The subdomain of `pauperwave.org` (domain acquired 2026-08-08) was the original plan, but if the PDF on the board is the real deliverable, a public web route may not be needed at all. That matters because the public route is not free: it would be the app's first genuinely unauthenticated page, needing anon-readable RLS on whatever backs it plus keeping `app/middleware/auth.global.ts`'s `publicPages` allowlist in sync with `nuxt.config.ts`'s `@nuxtjs/supabase` `redirectOptions`/`exclude` (see `CLAUDE.md`) — today the only public routes are `/login`, `/auth/callback`, `/logout`. Settle "PDF only" vs. "PDF + public page" before doing any of that work.
  - **Schema facts confirmed 2026-08-09** (audit: `docs/audits/2026-08-09-backup-docs-vs-live-schema.md`): nothing resembling a cross-tournament championship exists anywhere, so this is genuinely new — nothing to migrate. `tournaments.event_uuid` is **nullable**, so the regulation's one-off events (draft, sealed) and standalone tournaments already fit. Final placement should come from `tournament_standings.player_rank` (one row per player per tournament, unique per registration) rather than `tournament_round_results.position`, which is per-round — but `player_rank` is nullable, so nothing guarantees it's populated. `3-RLS-policies.md` in the backup docs proposes `public_read USING (true)` on `tournament_standings` and `tournaments`, which is exactly what a public standings page needs *if it was actually applied* — unverified.
  - **Open questions:** (a) the tie-break is specified only one level deep (highest single-event score) — undefined if two players match there too; (b) unclear whether "punteggio più alto in singolo evento" means highest points or best placement (equivalent under this table, but not if the table ever changes); (c) whether the January 2027 final, being itself an event, is excluded from the *2027* edition as well as the 2026 one.
  - **History goes back further than the mock assumes.** The user confirmed 2026-08-09 the ranking has run since at least 2022 — the mock in `server/api/cittadino.ts` only covers 2024/2025/2026 (`EDITIONS`), which understates the real archive by at least two years. Data for the older editions isn't available yet, but the user can retrieve it. Don't treat 2024 as the earliest real edition when backfilling `cittadino_editions` — confirm the actual start year first.
  - Found: 2026-08-09, user supplying the regulation after flagging the whole feature as missing (originally raised 2026-08-08, previously tracked in `docs/TODO.md`).
  - Next step: schema is migrated — insert the 2026 `cittadino_editions` row, then check `tournament_standings` coverage for 2026 tournaments before any UI work (this also decides which of them get `cittadino_edition_uuid` backfilled). Once the user retrieves the pre-2024 data, extend the mock/edition list to match the real start year rather than assuming 2024. The existing `leagues/single/Leaderboard.vue` stub (see `docs/TODO.md`) is closely related and may share the standings-rendering component.

## P2

- **Let a player change the status of their own "Carta Cercata" request.** `server/api/wanted-cards/[id]/status.post.ts` currently requires `requireManagementPermission` for *any* status change, including a player marking their own request "trovata"/"abbandonata" — confirmed wrong 2026-08-10 (`docs/architecture/permissions.md`): a player should have full control over their own request's status, the only action that should stay management-only is deleting it (`[id]/delete.post.ts`, unaffected). Fix: `status.post.ts` should accept either `requireManagementPermission` (any request) or an ownership check against the request's creator (own request only) — not `requireManagementPermission` alone. `[id]/update.post.ts` and `[id]/refresh-prices.post.ts` are out of scope for this item.
  - Found: 2026-08-10, while building the role/permissions matrix (`docs/architecture/permissions.md`).

- **Migrate magic-link auth from implicit flow to PKCE.** Current flow (`app/pages/auth/callback.vue`, `app/pages/login.vue`) relies on the implicit flow — the session token can briefly appear in the URL fragment/browser history. Given the app handles real associate PII, PKCE (customize email template with `{{ .TokenHash }}`, exchange via `verifyOtp({ token_hash, type: 'email' })` in the callback) is a worthwhile hardening step, though it requires callback-page and Supabase email-template changes.
